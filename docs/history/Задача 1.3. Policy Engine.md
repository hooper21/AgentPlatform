# RESULTS

## Что сделано

### 1. Enum ToolPolicy
`AgentPlatform.Core/Enums/PlatformEnums.cs` — `ToolPolicy { Read = 0, Write = 1, Destructive = 2 }`
уже зафиксирован контрактами задач 1.1/1.2; Policy Engine использует порядок значений
(read < write < destructive) для проверки повышения/понижения.

### 2. Core — правила Policy Engine
- `Core/Policy/ToolPolicyRules.cs` — `IsEscalation` и
  `ResolveEffectivePolicy(manifestPolicy, tenantPolicy, toolName)`: манифестная политика —
  потолок, tool_settings может только понизить её; повышение — `PolicyEscalationException`.
  Отсутствие tenant-политики → манифестная.
- `Core/Policy/PolicyGatePlanner.cs` — политика + `GateMode` → `GateRequirement`:
  - `always` → подтверждение всегда (read-тул тоже: это самый строгий режим);
  - `conditional` → `GateRequirement.Conditional(predicate)`; без валидного предиката —
    fail-closed как `always`;
  - `never` → гейт снимается только для read-политики; write/destructive остаются под
    гейтом (отключить серверную проверку можно только понижением политики);
  - `ResolveConditional(policy, satisfied)` — итог вычисления предиката: None либо
    UserConfirmation (read/write) / OperatorConfirmation (destructive).
- `Core/Policy/GatePredicateEvaluator.cs` — серверное вычисление
  `{"field": "amount", "op": "gt", "value": 50000}` на аргументах тула: операторы
  `eq, neq, gt, gte, lt, lte, in, contains`, вложенные поля (`order.amount`), числа и
  числовые строки, массивы. Некорректный предикат/аргументы — `GatePredicateException`
  (Runtime трактует как срабатывание гейта).
- `Core/Policy/ResolvedToolSettings.cs` — результат валидации: manifest/effective policy,
  `PolicySource`, `GateMode`, предикат и готовое `Requirement`.
- `Core/Validation/ToolSettingsValidator.cs` — строгая валидация конфига `tool_settings`
  (`policy` токенами read|write|destructive; `gate_settings` — jsonb `{mode, predicate?}`;
  неизвестные ключи запрещены; conditional требует предикат, предикат запрещён вне
  conditional; `value` обязателен). `CreateToolContext(...)` собирает `ToolContext` для
  Runtime из сохранённых настроек (отсутствующие настройки не превращаются в переопределения).
- `Core/Policy/PolicyEscalationException.cs`, `Core/Policy/GatePredicateException.cs`.
- `Core/Contracts/PolicyContracts.cs` — в `ToolContext` добавлен необязательный
  `GateMode? TenantGateMode = null` (режим из `tool_settings.gate_settings.mode`; null —
  настроек нет, действует `TenantPolicyContext.DefaultGateMode`). Изменение аддитивное,
  существующие позиционные вызовы не затронуты.

### 3. Runtime — `PolicyEngine : IPolicyEngine`
`AgentPlatform.Runtime/Policy/PolicyEngine.cs`:
- `GetGateRequirement(tool, tenant, session)` — действующая политика с повторной проверкой
  повышения при каждом вызове и режим гейта (`TenantGateMode ?? tenant.DefaultGateMode`);
  повышение → `PolicyEscalationException`, несовпадение tenant у сессии и контекста →
  `ArgumentException`;
- `EvaluateWithArguments(tool, tenant, session, arguments)` — вычисляет conditional-предикат
  на аргументах и возвращает итоговое требование (None / User / Operator); ошибка предиката
  или аргументов → подтверждение требуется (fail-closed);
- `ResolveEffectivePolicy(tool)` — действующая политика для потребителей (аудит/аналитика).
Регистрация в DI: `services.AddSingleton<IPolicyEngine, PolicyEngine>()`
(хост-композиция — задача 2.x).

### 4. Controller API — проверка конфига
`AgentPlatform.Controller/Endpoints/ToolSettingEndpoints.cs` —
`POST /api/v1/internal/tool-settings/validate`:
- запрос: `installationId`, `toolName`, `policy?`, `gateSettings?`, `manifestPolicy?`;
- если `manifestPolicy` не задан, политика читается из `connector_registry.manifest`
  установки (`ConnectorManifestValidator.Deserialize` + поиск тула);
- повышение → `422 policy_escalation`, нарушение формата → `422 invalid_tool_settings`,
  неизвестный манифест/тул → 404;
- ответ: manifest/tenant/effective policy, `policySource`, `gateMode`, `predicate`,
  `gateRequirement`. Endpoint зарегистрирован в `Controller/Program.cs`.

### 5. Юнит-тесты (`AgentPlatform.Tests/Policy`)
- `ToolPolicyRulesTests` — повышение (read→write, read→destructive, write→destructive),

- `ToolSettingsValidatorTests` — дефолты без настроек (`{}` и null → `always`),

  null-аргументы, неподдерживаемый оператор, нечисловое сравнение;
- `PolicyEngineTests` — строгий дефолт (read → UserConfirmation), `never` не отключает

## Решения и трактовки

1. **Манифест — потолок.** `tenant <= manifest`; любое повышение отклоняется и в Controller
   API (валидация до сохранения), и в Runtime (повторная проверка при вызове тула).
   Уже сохранённый некорректный конфиг не даёт агенту прав.
2. **Дефолт — самый строгий режим.** Нет `gate_settings` → `GateMode.Always` + манифестная
   политика; даже read-тул требует подтверждения. Снять гейт можно явным `never` после
   понижения политики до read. Write/destructive при `never` остаются под гейтом (fail-closed).
3. **Conditional.** `GetGateRequirement` возвращает `Conditional(predicate)`, поскольку
   аргументов ещё нет; `PolicyEngine.EvaluateWithArguments` вычисляет предикат и возвращает
   итоговое подтверждение. Предикат не исполняет код: только фиксированные операторы над JSON.
4. **Ошибка конфигурации не понижает безопасность.** Невалидный/отсутствующий предикат при
   `conditional` деградирует в `always`; ошибка вычисления предиката — в срабатывание гейта.
5. **Расширение контракта.** `ToolContext.TenantGateMode` — optional-параметр: без него
   реализовать `never`/`always` из `tool_settings.gate_settings` невозможно, а сигнатура
   `IPolicyEngine` осталась прежней.
