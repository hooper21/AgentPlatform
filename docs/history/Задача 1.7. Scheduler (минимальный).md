ЗАДАЧА: минимальный Scheduler как отдельный консольный сервис.

1. Конфигурация задач в БД: scheduled_runs (id, tenant_id, agent_id,
   cron-выражение, enabled, last_run).
2. По расписанию запускает сессию агента без входящего сообщения
   (RunAsync с системным триггером «плановый запуск»).
3. Пока без UI — управление через Controller API.
4. Тест: cron «каждую минуту» запускает тестового агента, результат —
   запись в messages сессии.

# RESULTS

## Итог

Реализован минимальный Scheduler как отдельный консольный сервис + управление расписаниями через Controller API.

### Что сделано

1. **Модель/хранилище `scheduled_runs`**
   - Таблица уже была в `InitialCreate`, новая миграция не требуется.
   - Добавлен Core-порт `IScheduledRunStore` и EF-реализация `EfScheduledRunStore`.
   - Все операции явно фильтруются по `tenant_id`.

2. **Cron-парсер без внешних библиотек**
   - `CronSchedule`: 5 полей (`минута час день_месяца месяц день_недели`), UTC.
   - Поддержка `*`, списков, диапазонов и шагов (`*/5`, `1-5`, `10-20/2`).
   - Классическое правило: если день месяца и день недели заданы одновременно — совпадение хотя бы по одному.
   - Некорректные выражения отклоняются Controller API с `400`.

3. **Плановый запуск агента**
   - `ScheduledRunRunner` раз в `Scheduler:PollIntervalSeconds` перебирает активных тенантов, читает их расписания и выбирает созревшие.
   - `ScheduledRunExecutor` создаёт новую сессию, служебный канал `system`, пишет в `messages` системный триггер `плановый запуск`, вызывает:
     ```csharp
     IOrchestrationRuntime.RunAsync(session, incomingMessage)
     ```
     где `incoming.Metadata["trigger"] = "schedule"`, `scheduled_run_id = <id>`.
   - Ответ агента сохраняется в `messages`, статус сессии обновляется.
   - `scheduled_runs.last_run_at` / `last_run_status` обновляются: `ok` при `Completed/PausedForGate`, `error` при исключении или `Degraded/Escalated`.
   - Ошибка одного расписания не останавливает worker и не влияет на следующие запуски.

4. **Controller API**
   - `GET/POST /api/v1/internal/tenants/{tenantId}/scheduled-runs`
   - `GET/PUT/DELETE /api/v1/internal/tenants/{tenantId}/scheduled-runs/{id}`
   - Проверяются: существование тенанта, принадлежность агента тенанту, валидность cron и длина `cron_expression` (≤ 100).

5. **Тесты**
   - `CronScheduleTests` — cron-парсер и edge-cases.
   - `ScheduledRunSchedulerTests.Every_minute_cron_launches_agent_and_writes_messages` — реальный `MafOrchestrationRuntime`, cron `* * * * *`, проверка сессии, двух записей в `messages` (системный триггер + ответ агента) и `last_run_status = ok`.
   - Тесты повторного запуска, ошибки отсутствующего агента, tenant-изоляции store и DI-сборки Scheduler.

**Результат тестов:** `230` пройдено, `0` сбоев.

### Как запустить

```powershell
# 1. Сборка
dotnet build AgentPlatform.sln

# 2. PostgreSQL (если локально через docker compose)
docker compose up -d postgres
# строка подключения — через ConnectionStrings__Postgres,
# иначе используется dev-фолбэк на localhost:5432

# 3. Controller API
dotnet run --project AgentPlatform.Controller
# локально: http://localhost:5265
# docker compose: http://localhost:8081

# 4. Scheduler (консольный сервис)
dotnet run --project AgentPlatform.Scheduler
```

Создать расписание «каждую минуту»:

```powershell
curl -X POST "http://localhost:5265/api/v1/internal/tenants/<tenantId>/scheduled-runs" `
  -H "Content-Type: application/json" `
  -d '{"agentId":"<agentId>","cronExpression":"* * * * *","enabled":true}'
```

Проверка в БД:

```sql
select id, tenant_id, agent_id, cron_expression, enabled, last_run_at, last_run_status
from scheduled_runs;

select s.id, s.user_ref, s.status, m.role, m.content, m.ts
from sessions s
join messages m on m.session_id = s.id
where s.user_ref = 'scheduler:<scheduled_run_id_без_дефисов>'
order by m.id;
```

Ожидаемо: новая сессия, в `messages` — `system: плановый запуск` и `assistant: <ответ агента>`, в `scheduled_runs` заполнены `last_run_at` и `last_run_status`.

### Ограничения / допущения

- Cron — 5 полей, время **UTC**; секунды и часовые пояса не поддерживаются.
- Запускается один экземпляр Scheduler; распределённой блокировки между экземплярами нет.
- Для планировщика создаётся служебный канал `channels.type = "system"` (по одному на тенант), потому что `sessions.channel_id` обязателен.
- Вызов тулов из Scheduler пока возвращает честную ошибку: MCP-транспорт — `TODO(2.2) contract`.
- LLM в Scheduler сейчас — `StubChatClientFactory` из LLM Gateway, как и в Gateway; реальный провайдер подключается отдельной задачей.
