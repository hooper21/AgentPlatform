# RESULTS

Готово. Ниже — итог по задаче, архитектурное обоснование, изменения, запуск и проверка гейт-ревью.

## 1. Выбор UI: Blazor Web App (Interactive Server)

Выбран **Blazor Web App** (Razor Components, интерактивный server render mode), а не React:

- Razor/Blazor входят в `Microsoft.AspNetCore.App` — **новых UI-библиотек не добавлено**;
- cookie-аутентификация ASP.NET Identity работает без CORS/JWT-обвязки;
- `tenant_id` берётся из claim пользователя, а не из заголовка;
- кабинет работает как BFF: страницы вызывают **Controller API** по HTTP, поэтому подтверждение гейта действительно проходит через Controller → `ResumeAsync`;
- React потребовал бы Node/npm, отдельный build-pipeline и дублирование инфраструктуры.

## 2. Что реализовано

### Логин и роли
- ASP.NET Identity Core поверх существующей таблицы `users` (без новых identity-таблиц): `UserManager`, `SignInManager`, cookie scheme, PBKDF2-хеш из seed.
- Роли `admin / operator / viewer`:
  - `admin` — полный CRUD агентов/коннекторов;
  - `operator` — просмотр + решения по гейтам;
  - `viewer` — только просмотр.
- Роль проверяется в UI и **серверно** при решении по гейту (Controller читает `users.role` по `actorId`).
- Опциональный seed демо-пользователей `operator@demo.local` / `viewer@demo.local` (`AGENTPLATFORM_SEED_ROLE_USERS=true`, пароль админа).

### Агенты
- CRUD через Controller API tenant-first.
- Изменение публикует **новую неизменяемую версию** (`agent_versions`, `agents.current_version`), version pinning не ломается.
- Тулы включаются с политикой и режимом гейта; политики проверяются `ToolSettingsValidator`:
  - повышение манифестной политики отклоняется (`policy_escalation`);
  - понижение разрешено;
  - клиент ограничивает варианты select-а и повторно проверяет rank перед сохранением.

### Коннекторы
- Реестр `connector_registry`: импорт манифеста EchoTools из Connector Host при старте Controller + ручной `POST /api/v1/internal/connector-registry/sync`.
- Установка коннектора с credentials:
  - AES-256-GCM;
  - KMS-заглушка (мастер-ключ из `AGENTPLATFORM_SECRETS_MASTER_KEY`, `TODO(kms)`);
  - в БД — только `credential_ref` (`tenant_secrets`), значения наружу не возвращаются;
  - поля credentials валидируются по манифесту.
- При установке создаются `tool_settings` по умолчанию (`read → never`, `write/destructive → always`).
- CRUD `tool_settings` через API.

### Диалоги и HITL
- `POST /dialogs` — сообщение → `IOrchestrationRuntime.RunAsync`.
- Пауза: в `approvals` создаётся pending-заявка, сессия → `awaiting_gate`, карточка гейта отдаётся в API.
- `approvals/{approvalId}/decision` → проверка роли → `ResumeAsync`:
  - `approve` исполняет тул;
  - `reject` — тул не исполняется, диалог продолжается;
  - решение фиксируется в `approvals` внутри `GateExecutor`.
- Сессия/сообщения/чекпоинты/заявки — в PostgreSQL, поэтому пауза и подтверждение переживают рестарт Controller.
- Сообщения, появившиеся в чекпоинте при resume, переносятся в журнал `messages`.

### MCP
- Controller вызывает EchoTools **только через Connector Host** (MCP streamable HTTP, `ModelContextProtocol` 2.4.0 — SDK из фиксированного стека README).
- MCP endpoint Connector Host: `/mcp`.
- Для EchoTools URL берётся из `ConnectorHost:BaseUrl`, для внешних — из `connector_installations.external_url`.

### Демо-LLM
- В `LlmGateway` добавлен детерминированный `DemoChatClient`:
  - `write: <текст>` → `echo_write`;
  - `read: <текст>` → `echo_read`;
  - после результата тула/отказа повторно тул не вызывает.
- Это позволяет пройти гейт-ревью без ключей внешнего LLM. `TODO(2.x)` — заменить реальным LLM Gateway.

## 6. Как проверить гейт-ревью

### Через кабинет
1. Войти как `admin`.
2. «Коннекторы» → установить `echo`.
3. «Агенты» → создать агента, включить `echo_read` (read/never) и `echo_write` (write/always).
4. «Диалоги» → новый диалог, сообщение `write: тест`.
5. Появится карточка гейта → «Подтвердить».
6. В сообщениях появятся `tool: echo(write): тест` и ответ ассистента.

Для проверки рестарта: на шаге 5 остановить Controller (`docker compose restart controller`), затем подтвердить — сессия не потеряется.

### Через API
```powershell
$api='http://localhost:8081'
$tenant=(Invoke-RestMethod "$api/api/v1/internal/tenants")[0].id
$registry=(Invoke-RestMethod "$api/api/v1/internal/tenants/$tenant/connector-registry")[0].id
$installation=(Invoke-RestMethod -Method Post "$api/api/v1/internal/tenants/$tenant/connector-installations" `
  -ContentType 'application/json' -Body (@{ registryId=$registry } | ConvertTo-Json)).id

$agent=(Invoke-RestMethod -Method Post "$api/api/v1/internal/tenants/$tenant/agents" `
  -ContentType 'application/json' -Body (@{
    name='echo-agent'; systemPrompt='test agent'; model='demo-model';
    tools=@(
      @{installationId=$installation; toolName='echo_read'; policy='read'; gateSettings='{"mode":"never"}'},
      @{installationId=$installation; toolName='echo_write'; policy='write'; gateSettings='{"mode":"always"}'}
    )
  } | ConvertTo-Json -Depth 6)).id

$dialog=Invoke-RestMethod -Method Post "$api/api/v1/internal/tenants/$tenant/dialogs" `
  -ContentType 'application/json' -Body (@{ agentId=$agent; message='write: test' } | ConvertTo-Json)

# рестарт Controller здесь
$actor=(Invoke-RestMethod "$api/api/v1/internal/tenants/$tenant/users")[0].id
Invoke-RestMethod -Method Post `
  "$api/api/v1/internal/tenants/$tenant/dialogs/$($dialog.sessionId)/approvals/$($dialog.pendingApproval.approvalId)/decision" `
  -ContentType 'application/json' `
  -Body (@{ decision='approve'; comment='ok'; actorId=$actor } | ConvertTo-Json)
```

### Cron
```powershell
Invoke-RestMethod -Method Post "$api/api/v1/internal/tenants/$tenant/scheduled-runs" `
  -ContentType 'application/json' `
  -Body (@{ agentId=$agent; cronExpression='* * * * *'; enabled=$true } | ConvertTo-Json)
```
После тика Scheduler: `lastRunStatus=ok`, в `GET /dialogs` появляется сессия `scheduler:<runId>`.
