переведи инжест-пайплайн на него.

1. Контракт (черновик сигнатур продумай по аналогии с IChannelAdapter):
   - GetSourceInfo() → описание провайдера (название, тип подключения,
     настраиваемые параметры);
   - TestConnection(config) → статус связи;
   - FetchAll(config, since: null) → поток страниц: {externalId, title,
     content, metadata (автор, дата изменения, URL, пространство/папка),
     isDeleted?};
   - FetchIncremental(config, cursor) → поток изменений + новый cursor.
   Провайдер НЕ знает про чанкинг, эмбеддинги и pgvector — он отдаёт
   сырой контент с метаданными. Всё после — общий пайплайн.

   становятся реализациями контракта (DocumentProvider, SiteProvider,
   FaqProvider). Поведение не меняется — тесты 2.1 остаются зелёными.

3. Курсор инкремента: у источника хранится last_cursor; синхронизация
   по расписанию и по вебхуку (webhook endpoint — общий для всех
   провайдеров, маршрутизация по source_id).

4. Удалённые страницы: isDeleted=true → чанки источника удаляются
   при синхронизации (в knowledge_chunks — по externalId в metadata).

5. Схема: миграцией добавь в knowledge_sources поля provider_type
   (строковый, по умолчанию legacy для старых типов), config jsonb
   (подключение), credentials_ref (ссылка на секрет), last_cursor text,
   sync_schedule varchar.

6. UI кабинета: на экране «Знания» — выбор типа источника из реестра
   провайдеров (сейчас: документ, сайт, FAQ; список расширяем).

7. Юнит-тесты: round-trip через контракт для трёх встроенных провайдеров,
   инкремент (cursor двигается), удаление страниц, tenant-изоляция.

## 1. Контракт Core

`AgentPlatform.Core/Abstractions/IKnowledgeProvider.cs` — по аналогии с `IChannelAdapter`:

```csharp
KnowledgeProviderInfo GetSourceInfo();
Task<KnowledgeConnectionStatus> TestConnection(KnowledgeProviderConfig config, CancellationToken ct = default);
IAsyncEnumerable<KnowledgePage> FetchAll(KnowledgeProviderConfig config, DateTimeOffset? since = null, CancellationToken ct = default);
IAsyncEnumerable<KnowledgeChange> FetchIncremental(KnowledgeProviderConfig config, string? cursor = null, CancellationToken ct = default);
```

DTO (`Core/Dto/KnowledgeProviderDtos.cs`):
- `KnowledgeProviderInfo` — `ProviderType`, `DisplayName`, `ConnectionType` (file/http/manual), `Description`, `Parameters`, `SupportsIncremental`, `SupportsWebhooks`;
- `KnowledgeProviderConfig` — `Title`, `Location`, `Content`, `CredentialsRef`, `Parameters`;
- `KnowledgePage` — `ExternalId`, `Title`, `Content`, `Metadata` (автор, дата изменения, URL, пространство/папка), `IsDeleted`, `Heading`, `Position`, `Cursor`;
- `KnowledgeChange` — страница изменения + новый курсор (tombstone — `Page.IsDeleted`).

Провайдер не знает про чанкинг, эмбеддинги, pgvector и tenant-изоляцию: только подключение и сырые страницы.

## 2. Провайдеры и пайплайн

- `DocumentProvider` (MD/TXT, разделы Markdown, курсор = время изменения файла), `SiteProvider` (robots.txt, один уровень, курсор = время обхода, инкремент по `Last-Modified`), `FaqProvider` (курсор = SHA-256 контента).
- `KnowledgeProviderRegistry` — маршрутизация `provider_type → IKnowledgeProvider`; для старых строк с `provider_type='legacy'` провайдер берётся по legacy-колонке `type`.
- `KnowledgeIngestService`:
  - полная синхронизация — `FetchAll` → чанки → `ReplaceSourceChunksAsync`;
  - инкрементальная — `FetchIncremental(last_cursor)` → постраничная замена чанков;
  - `isDeleted=true` → удаление чанков по `metadata.external_id`;
  - `last_cursor` сохраняется в `knowledge_sources.last_cursor`, дублируется в `index_meta.cursor` для совместимости 2.1;
  - scheduled/вебхук вызывают `SyncAsync`: инкремент при поддержке провайдером и наличии курсора, иначе полная переиндексация.
- `KnowledgeReindexWorker` читает `sync_schedule` (фолбэк — `index_meta.reindex_cron`) и вызывает `SyncAsync`.
- `IKnowledgeVectorStore` расширен `ReplacePageChunksAsync` и `DeletePageChunksAsync` (in-memory и pgvector).

## 3. API Knowledge Service

- `GET /api/knowledge/providers` — реестр провайдеров;
- `POST /api/knowledge/providers/{providerType}/test-connection` — `TestConnection`;
- `POST /api/knowledge/sources` — тип из реестра, `config`, `credentialsRef`, `syncSchedule`;
- `POST /api/knowledge/sources/{id}/sync` — инкремент (fallback на полный);
- `POST /api/knowledge/sources/{id}/reindex` — полная переиндексация;
- `POST /api/knowledge/webhooks/{sourceId}` — общий вебхук, маршрутизация по `source_id`, тенант определяется по источнику.

## Явные ограничения

- **Tombstones провайдеров**: document/site не отслеживают исчезнувшие страницы между инкрементами (нет внешнего состояния); удаление гарантируется контрактом для провайдеров, отдающих `isDeleted=true`, либо полной переиндексацией.
- **Site incremental** фильтрует по HTTP `Last-Modified`; если сервер его не отдаёт, страница считается изменённой.
- **Вебхук** в v1 не проверяет подпись/формат payload: это провайдер-специфичный контракт (`TODO(contract)`), маршрутизация по `source_id` уже реализована.
- **provider_type='legacy'** у мигрированных строк — осознанно: пайплайн находит провайдера по legacy-колонке `type`, поведение 2.1 не меняется.
- Инжест по-прежнему синхронный (inline); очередь фоновой индексации — отдельная задача.
