# Установка, настройка и администрирование

Документ описывает, как развернуть решение, какие настройки оно читает и что делать
администратору в повседневной работе. Это общее руководство, а не пошаговая спецификация
каждого параметра.

## 1. Что требуется

Для развёртывания через Docker:

- Docker и Docker Compose на хосте (предполагается один VPS);
- свободные порты: 8080–8084 (сервисы платформы), 5432 (PostgreSQL), 6379 (Redis).

Для локальной разработки дополнительно:

- .NET SDK 10 (решение собирается на `net10.0`);
- PostgreSQL (в идеале образ с pgvector) и Redis — либо локально, либо контейнерами
  `postgres` / `redis` из `docker-compose.yml`.

## 2. Установка через Docker Compose

Все команды выполняются из каталога `src` (там лежат `docker-compose.yml`, `Dockerfile`
и `.env.example`).

1. Создайте файл окружения:

   ```bash
   cp .env.example .env
   ```

2. Заполните `.env`:

   | Переменная | Назначение |
   |---|---|
   | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | база и учётная запись PostgreSQL |
   | `AGENTPLATFORM_SEED_ADMIN_PASSWORD` | **обязательна**: пароль admin-пользователя демо-тенанта |
   | `AGENTPLATFORM_SEED_ADMIN_EMAIL` | e-mail admin (по умолчанию `admin@demo.local`) |
   | `AGENTPLATFORM_SEED_TENANT_NAME` | имя демо-тенанта (по умолчанию `Demo Tenant`) |
   | `AGENTPLATFORM_SEED_ROLE_USERS` | `true` — дополнительно создать `operator@demo.local` и `viewer@demo.local` |
   | `AGENTPLATFORM_SECRETS_MASTER_KEY` | base64-ключ AES-256 (32 байта) для шифрования секретов тенантов |
   | `ASPNETCORE_ENVIRONMENT` | `Development` или `Production` |
   | `AGENTPLATFORM_IMAGE_TAG` | тег локально собираемых образов |

   Ключ шифрования удобно сгенерировать командой `openssl rand -base64 32`.

3. Соберите и запустите:

   ```bash
   docker compose up -d --build
   ```

   Compose поднимает PostgreSQL, Redis, одноразовую задачу `migrate` (накатывает миграции и
   создаёт демо-тенанта и пользователей), затем сервисы платформы. Задача `migrate`
   выполняется один раз и завершается; остальные сервисы ждут её успешного завершения.

4. Проверьте состояние: у каждого сервиса есть `GET /health`, Compose-проверки здоровья
   встроены в описание сервисов.

Публикуемые адреса (снаружи хоста):

| Сервис | Порт | Назначение |
|---|---|---|
| Gateway | 8080 | приём сообщений канала, SSE-поток |
| Controller | 8081 | внутренний API платформы, бэкенд кабинета |
| TenantApp | 8082 | кабинет тенанта (браузер) |
| ConnectorHost | 8083 | MCP-сервер коннекторов, манифесты |
| Knowledge | 8084 | сервис знаний (каркас) |
| PostgreSQL | 5432 | база данных |
| Redis | 6379 | rate-limit и кеш конфигурации |

Scheduler портов не публикует — это фоновый worker.

5. Вход в кабинет: откройте `http://<host>:8082`, войдите как `admin@demo.local` с паролем
   из `AGENTPLATFORM_SEED_ADMIN_PASSWORD`. Если включён `AGENTPLATFORM_SEED_ROLE_USERS`,
   доступны также `operator@demo.local` и `viewer@demo.local` с тем же паролем.

## 3. Локальный запуск (разработка)

1. Соберите решение: `dotnet build AgentPlatform.sln`.
2. Поднимите PostgreSQL и Redis (можно только эти два сервиса из compose:
   `docker compose up -d postgres redis`).
3. Подготовьте БД — миграции и seed выполняет любой из сервисов с поддержкой команд:

   ```bash
   dotnet run --project AgentPlatform.TenantApp -- --migrate --seed
   ```

   Строка подключения берётся из `ConnectionStrings__Postgres` (при отсутствии используется
   локальный фолбэк), а пароль администратора для seed задаётся переменной
   `AGENTPLATFORM_SEED_ADMIN_PASSWORD` — без неё seed не выполнится (см. раздел 4).
4. Запустите сервисы (порты из `launchSettings.json`):

   | Сервис | Адрес |
   |---|---|
   | ConnectorHost | http://localhost:5286 |
   | Controller | http://localhost:5265 |
   | Gateway | http://localhost:5110 |
   | TenantApp | http://localhost:5163 |
   | Knowledge | http://localhost:5281 |
   | Scheduler | без порта (worker) |

5. Для локальной работы достаточно Controller + ConnectorHost + TenantApp; Gateway нужен
   только для проверки канала виджета, Scheduler — для проверки расписаний.

Полезно для разработки: `Gateway:RateLimit:Storage=memory` переключает rate-limit на
память процесса, а отсутствие строки подключения Redis переводит кеш конфигурации агента
в память (Redis в этом случае не обязателен).

## 4. Настройка

Строки подключения и секреты в файлах конфигурации не хранятся. Строка подключения к
PostgreSQL берётся из переменной окружения `ConnectionStrings__Postgres`; если она не
задана, используется локальный фолбэк на параметры по умолчанию (`localhost:5432`,
база/пользователь/пароль `agentplatform` — совпадает с docker-compose, только для
разработки).

Параметры по сервисам:

| Сервис | Ключ (файл / переменная) | Смысл |
|---|---|---|
| сервисы с БД | `ConnectionStrings__Postgres` | строка подключения к PostgreSQL |
| Controller | `AGENTPLATFORM_SECRETS_MASTER_KEY` | base64-ключ AES-256 для Secret Service (KMS-заглушка) |
| миграции/seed | `AGENTPLATFORM_SEED_ADMIN_PASSWORD` | обязательный пароль admin для seed |
| миграции/seed | `AGENTPLATFORM_SEED_ADMIN_EMAIL`, `AGENTPLATFORM_SEED_TENANT_NAME`, `AGENTPLATFORM_SEED_ROLE_USERS` | параметры демо-тенанта |
| сервисы с БД | `AGENTPLATFORM_DB_DETAILED_ERRORS` | подробные ошибки БД (только для разработки) |
| Gateway | `Gateway:RateLimit:Storage/Capacity/TokensPerSecond/Cost/KeyTtl/KeyPrefix` | параметры rate-limit тенанта |
| Gateway | `Gateway:Llm:Retries`, `Gateway:Llm:RetryDelay` | повторы вызова модели |
| Gateway | `Gateway:Widget:Secrets:<tenant_id>` | секрет подписи JWT виджета по тенанту |
| Gateway | `Redis__ConnectionString` | Redis для rate-limit |
| Controller | `ConnectorHost:BaseUrl`, `McpPath`, `CallTimeoutSeconds` | адрес и таймаут MCP-транспорта |
| Controller, Scheduler | `Redis__ConnectionString` | Redis для кеша конфигурации агента |
| TenantApp | `Controller:BaseUrl` | адрес Controller API |
| Scheduler | `Scheduler:PollIntervalSeconds` | период тика планировщика (5–3600, по умолчанию 30) |

В docker-compose значения по умолчанию уже прописаны (адреса `postgres`, `redis`,
`connector-host`, `controller`), поэтому вручную донастраивать нужно только секреты и
пароли.

Срок жизни HITL-гейта (24 часа), TTL кеша конфигурации (60 секунд) и переопределения
таймаута по тенантам задаются в коде при регистрации Runtime (`AgentRuntimeOptions`) и
пока не выведены в конфигурацию. Реальные провайдеры модели и KMS тоже ещё не подключены —
это места, помеченные в коде как `TODO`.

## 5. Администрирование

### 5.1. Тенанты и пользователи

Тенант и пользователей создаёт seed (таблицы `tenants`, `users`). UI или API для управления
тенантами и пользователями в текущей версии нет: новые записи добавляются в БД (пароль
пользователя — в виде PBKDF2-хеша).

Роли пользователей кабинета: `admin` (полная настройка), `operator` (просмотр и решения по
гейтам), `viewer` (только просмотр). Роль решения по гейту проверяется на сервере по
таблице пользователей, а не только в интерфейсе.

Статус тенанта `blocked` останавливает плановые запуски (Scheduler обрабатывает только
тенантов со статусом `active`) и блокирует приём сообщений через Gateway (ответ
`tenant_blocked`).

Пароль пользователя хранится как PBKDF2-хеш. Политика пароля кабинета: не короче 8
символов, с заглавной, строчной буквой и цифрой; после 5 неудачных попыток вход блокируется
на 5 минут.

### 5.2. Агенты

Агенты настраиваются в кабинете (страница «Агенты»): имя, системный промпт, модель,
маршрутизация, лимиты `max_turns` / `max_tool_calls`, список включённых тулов с политикой и
режимом гейта.

- Каждое сохранение публикует новую версию; версии неизменяемы.
- Идущие диалоги продолжают работать на той версии, с которой начались. Новая версия
  применяется к новым сессиям.
- Откат задуман как переключение указателя `agents.current_version`, отдельного API/UI для
  этого пока нет.
- Политику тула можно только понизить (например, `write` → `read`); попытка повысить
  отклоняется и в интерфейсе, и в Controller. Режим гейта в кабинете — «всегда» или «никогда».
- Удалить агента, у которого есть сессии или расписания, нельзя — API вернёт конфликт.

### 5.3. Коннекторы и секреты

- Каталог коннекторов синхронизируется из Connector Host: автоматически при старте
  Controller (несколько попыток) и вручную — кнопкой обновления/запросом
  `POST /api/v1/internal/connector-registry/sync`.
- Установка коннектора выполняется в кабинете (страница «Коннекторы»). Значения
  credentials передаются только на вход, шифруются AES-256-GCM и сохраняются в таблице
  `tenant_secrets`; API возвращает лишь ссылку на секрет.
- Состояние установки (`active` / `disabled`) переключается в кабинете; удаление установки
  удаляет и её секрет.
- Настройки тулов в кабинете минимальны: включение тула, политика (только понижение) и
  режим гейта «всегда / никогда». Режим с условием (`conditional`) задаётся через настройки
  тулов в API — валидация доступна по `POST /api/v1/internal/tool-settings/validate`.
- Мастер-ключ Secret Service хранится вне БД (переменная окружения, KMS-заглушка). При его
  смене ранее сохранённые секреты прочитать нельзя — их нужно сохранить заново через
  повторную установку/обновление коннектора. Ключ следует хранить в защищённом месте и
  включать в резервные копии отдельно от БД.

### 5.4. Диалоги и подтверждения

- Кабинет: страница «Диалоги» показывает сессии, статус, визитера и ожидающий гейт.
  В карточке диалога видны сообщения, маскированные аргументы действия и срок истечения
  заявки.
- Подтверждение и отклонение доступны ролям admin и operator. Решение фиксируется с автором
  и временем; комментарий передаётся в Runtime вместе с решением.
- Срок жизни заявки (по умолчанию 24 часа) фиксируется при паузе. Просроченная заявка при
  попытке подтверждения трактуется как отказ (`expired`) — действие не исполняется;
  фоновой отмены сессий по таймеру нет, сессия остаётся в ожидании до решения.
- Записи `approvals`, `messages`, `checkpoints` хранятся в PostgreSQL, поэтому пауза
  переживает перезапуск сервисов.

### 5.5. Расписания

Управление — через Controller API (UI нет):

- `GET/POST /api/v1/internal/tenants/{tenantId}/scheduled-runs`;
- `GET/PUT/DELETE /api/v1/internal/tenants/{tenantId}/scheduled-runs/{id}`.

Cron-выражение — пять полей (`минута час день_месяца месяц день_недели`), поддерживаются
`*`, списки, диапазоны и шаги. Время — UTC. Некорректное выражение отклоняется при
сохранении; агент должен существовать в этом тенанте. Отключённые расписания
(`enabled=false`) не запускаются. Итог последнего запуска пишется в `last_run_status`.

### 5.6. Схема БД, обновление и резервное копирование

- Миграции накатываются командой `--migrate` (в compose — сервисом `migrate`, локально —
  `dotnet run --project AgentPlatform.TenantApp -- --migrate`). Повторный запуск безопасен.
- Seed идемпотентен: тенант и пользователи создаются только если их ещё нет, дубли не
  появляются. Пароли существующих пользователей повторный seed не меняет.
- Обновление версии: собрать образы с новым тегом (`AGENTPLATFORM_IMAGE_TAG`) и выполнить
  `docker compose up -d --build`. Перед обновлением имеет смысл прогнать `migrate`.
- Данные лежат в томах `pgdata` (PostgreSQL) и `redisdata` (Redis). Для резервного
  копирования достаточно выгружать базу PostgreSQL; Redis содержит только rate-limit и кеш
  и восстанавливается пустым.
- Мастер-ключ секретов в БД не хранится — без него зашифрованные секреты не прочитать,
  поэтому ключ нужно хранить отдельно и вместе с резервной копией БД.

### 5.7. Наблюдаемость и ограничения эксплуатации

- Логи — стандартные логи ASP.NET Core и Worker-сервиса; уровни задаются в `appsettings`.
  OpenTelemetry, Jaeger и метрики в текущей версии не подключены.
- Health-check: `GET /health` у Gateway, Controller, TenantApp, ConnectorHost, Knowledge.
  У Scheduler health-эндпоинта нет — контролируется по логам и по `last_run_status`.
- Ограничения текущей версии, важные при эксплуатации:
  - SSE-поток и подписки хранятся в памяти процесса Gateway — рассчитано на одну реплику;
  - Scheduler рассчитан на один экземпляр: несколько экземпляров не координируются;
  - модель — заглушка/демо, поэтому качество ответов определяется не провайдером, а
    тестовой логикой;
  - тулы работают только в цепочке кабинет → Controller → Connector Host;
  - поиск по знаниям и панель оператора платформы отсутствуют.

### 5.8. Типичные проблемы и что проверить

| Симптом | Что проверить |
|---|---|
| `migrate` завершился с ошибкой | доступность PostgreSQL, `ConnectionStrings__Postgres`, журнал миграций |
| Seed падает с требованием `AGENTPLATFORM_SEED_ADMIN_PASSWORD` | не задан пароль администратора для seed |
| Вход в кабинет не работает | пользователь есть в таблице `users`, пароль соответствует политике, тенант пользователя корректен |
| Каталог коннекторов пуст | Connector Host недоступен; посмотрите лог синхронизации и повторите `POST /api/v1/internal/connector-registry/sync` |
| Вызов тула возвращает ошибку «connector has no external URL» | платформенный коннектор должен обслуживаться Connector Host, для внешнего — задан `external_url` |
| Диалог в кабинете не начинается | агент существует в тенанте и у него задана текущая версия |
| Gateway отвечает ошибкой о канале или агенте | у тенанта нет активного виджет-канала или агента, привязанного к каналу |
| Gateway отвечает `tenant_blocked` | тенант в статусе `blocked` |
| Gateway отвечает 401 по JWT | секрет тенанта не задан в `Gateway:Widget:Secrets:<tenant_id>`, токен просрочен или подписан не HS256 |
| Сессия получает fallback-ответ | модель недоступна: сессия помечается `degraded`, проверьте логи повторов и провайдера |
| Секреты коннектора «не читаются» после перезапуска | сменился `AGENTPLATFORM_SECRETS_MASTER_KEY`; сохраните секреты заново |

### 5.9. Проверка работоспособности

- Сборка: `dotnet build AgentPlatform.sln`.
- Тесты: `dotnet test AgentPlatform.sln` (внешние PostgreSQL, Redis и модель не нужны).
- После установки: открыть кабинет, войти admin-пользователем, убедиться, что в «Коннекторах»
  виден `echo`, установить его, создать агента с включёнными `echo_read` и `echo_write`,
  создать диалог с сообщением `write: тест` и подтвердить гейт.
- Gateway проверяется отдельно: нужен активный виджет-канал тенанта и JWT, подписанный его
  секретом; ответ приходит и в ответе на `POST`, и в SSE-потоке.
