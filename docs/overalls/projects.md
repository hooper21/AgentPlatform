# Проекты решения

Решение состоит из одиннадцати проектов .NET, объединённых в `AgentPlatform.sln`.
Шесть из них — исполняемые сервисы (Web API или Worker), четыре — библиотеки и один —
проект тестов. Ниже — назначение каждого проекта и его связи с остальными.

## Краткая карта

| Проект | Тип | Роль |
|---|---|---|
| AgentPlatform.Core | библиотека | контракты, типы, правила и валидаторы платформы |
| AgentPlatform.Infrastructure | библиотека | EF Core, PostgreSQL, репозитории, секреты, seed |
| AgentPlatform.Runtime | библиотека | оркестратор агента, граф, Policy Engine |
| AgentPlatform.LlmGateway | библиотека | абстракция модели (`IChatClient`) и заглушки |
| AgentPlatform.Gateway | веб-сервис | вход канала виджета, сессии, SSE, rate-limit |
| AgentPlatform.Controller | веб-сервис | внутренний API платформы и бэкенд кабинета |
| AgentPlatform.TenantApp | веб-приложение | кабинет тенанта (Blazor) |
| AgentPlatform.ConnectorHost | веб-сервис | MCP-сервер коннекторов |
| AgentPlatform.Knowledge | веб-сервис | каркас сервиса знаний (RAG) |
| AgentPlatform.Scheduler | worker | плановые (cron) запуски агентов |
| AgentPlatform.Tests | тесты (xUnit) | проверка гейтов, политик, лимитов, resume и т.д. |

Зависимости по ссылкам проектов:

- `Core` не зависит ни от чего;
- `LlmGateway` и `Infrastructure` зависят от `Core`;
- `Runtime` зависит от `Core` и `LlmGateway`;
- `Gateway`, `Controller`, `Scheduler` зависят от `Core`, `Infrastructure`, `Runtime` и
  `LlmGateway`;
- `TenantApp` зависит от `Core` и `Infrastructure` (доступ к БД только для входа и
  служебных эндпоинтов, данные кабинета — через Controller);
- `ConnectorHost` зависит только от `Core` (манифест и его схема);
- `Knowledge` зависит от `Core` и `Infrastructure`;
- `Tests` ссылается на все проекты.

## AgentPlatform.Core

**Назначение** — единый набор контрактов и типов, на которые опираются все слои. Здесь нет
ни базы данных, ни HTTP, ни внешних зависимостей.

**Что внутри:**

- абстракции платформы: `IOrchestrationRuntime`, `IChannelAdapter`, `IPolicyEngine`,
  `IToolInvoker`, `ISecretService`, `ITenantContext`, `ITenantEntity`,
  `IAgentConfigStore`, `ICheckpointStore`, `IApprovalStore`, `IScheduledRunStore`,
  `ITenantGateTimeoutProvider`, `ITenantScopedRepository<T>`, `IGlobalRepository<T>`;
- контракты данных: манифест коннектора и его JSON Schema (встроенный ресурс),
  нейтральное состояние сессии и его сериализация (`StateContract`), данные гейта,
  конфигурация версии агента для Runtime, запрос/результат вызова тула, чекпоинт;
- DTO обмена между сервисами: контекст сессии и результат хода, сообщения каналов,
  карточка подтверждения и уведомление об эскалации, заявка HITL, запросы к знаниям,
  состояние сервиса для health-check;
- правила и проверки: `ToolPolicyRules` (понижение/повышение политики), `PolicyGatePlanner`,
  `GatePredicateEvaluator` (условия гейта), валидаторы манифеста, настроек тулов, правил
  агента и payload гейта;
- инфраструктурные мелочи, общие для слоёв: `PlatformJson` (snake_case для jsonb и
  camelCase для HTTP), `PiiMasker`, токены enum для БД, cron-разбор `CronSchedule`.

**Связи** — используется всеми проектами решения. Изменение контракта здесь затрагивает всё,
поэтому расширение контрактов вынесено в отдельные задачи.

## AgentPlatform.Infrastructure

**Назначение** — весь доступ к данным и к хранилищу секретов: PostgreSQL через EF Core,
репозитории, миграции, наполнение БД, шифрование секретов тенантов.

**Что внутри:**

- `AgentPlatformDbContext` — модель БД: 19 таблиц (тенанты и пользователи, реестр и
  установки коннекторов, настройки тулов, агенты и их версии, каналы, источники и чанки
  знаний, сессии, сообщения, чекпоинты, заявки HITL, аудит тулов, usage, расписания,
  шаблоны решений, секреты тенантов). Имена таблиц и колонок — snake_case; jsonb-документы
  пишутся по правилам `PlatformJson`. Миграции лежат в проекте;
- инварианты, проверяемые кодом при сохранении: обязательность `tenant_id` при вставке,
  append-only для `tool_audit`, валидация payload заявки и правил версии агента;
- `AuditingInterceptor` — проставляет `created_at` / `updated_at` (UTC);
- репозитории: `TenantScopedRepository<T>` (автоматический фильтр по тенанту) и
  `GlobalRepository<T>` (глобальные таблицы);
- реализации портов Runtime: хранилище конфигурации агента, чекпоинтов, заявок,
  расписаний;
- `TenantContext` — scoped-контекст текущего тенанта;
- `AesKmsSecretService` — шифрование секретов AES-256-GCM и хранение их в таблице
  `tenant_secrets`; наружу отдаются только ссылки `secret://local/…`;
- `DatabaseSeeder` (идемпотентный seed тенанта и пользователей), `DataMaintenance`
  (команды `--migrate` и `--seed`), `Pbkdf2PasswordHasher`.

**Связи** — используется Gateway, Controller, TenantApp, Scheduler, Knowledge и тестами.
Зависит только от `Core`.

## AgentPlatform.Runtime

**Назначение** — сам агент: сборка агента из конфигурации, граф диалога, проверка политик,
пауза и возобновление у HITL-гейтов. Реализация спрятана за `IOrchestrationRuntime`, поэтому
её можно заменить, не меняя остальные сервисы.

**Что внутри:**

- `MafOrchestrationRuntime` — реализация `IOrchestrationRuntime` на
  Microsoft.Agents.AI.Workflows. Метод `RunAsync` проводит ход диалога, `PauseAsync`
  сохраняет чекпоинт и заявку, `ResumeAsync` продолжает граф с решения по гейту;
- граф `OrchestrationGraph` и узлы-исполнители: старт хода, диалог (LLM), вызов тула,
  гейт, эскалация, завершение. Топология подписана константой (хеш подписи), которая
  проверяется при возобновлении — чекпоинт от другой версии графа не «подхватится»;
- `AgentFactory` — собирает агента строго той версии, с которой начата сессия
  (version pinning), с системным промптом, моделью и активными тулами; конфигурация
  кешируется (Redis или память, TTL 60 секунд);
- `PolicyEngine` — серверная проверка политик тулов и требования подтверждения, включая
  вычисление условий по аргументам вызова; ошибочные условия трактуются как требующие
  подтверждения;
- `AgentRuntimeOptions` — TTL кеша конфигурации, срок жизни гейта (24 часа и переопределение
  по тенанту), страховочный предел супершагов;
- кеши конфигурации: `RedisAgentConfigCache` и `InMemoryAgentConfigCache`.

**Связи** — используется Gateway, Controller и Scheduler; сам зависит от `Core`,
`LlmGateway` и портов, реализации которых регистрирует хост-сервис
(`IAgentConfigStore`, `ICheckpointStore`, `IApprovalStore`, `IToolInvoker`,
`IChatClientFactory`).

## AgentPlatform.LlmGateway

**Назначение** — единая абстракция обращения к модели и заготовки на случай отсутствия
провайдера.

**Что внутри:**

- `IChatClientFactory` — фабрика клиента под конкретную модель агента/тенанта;
- `PlatformChatClient` — обёртка над `IChatClient`, место для учёта токенов, выбора модели и
  трейсинга (пока просто проксирует вызовы);
- `StubChatClient` и `StubChatClientFactory` — заглушка, возвращает текст без обращения к
  внешним API (используется Gateway и Scheduler);
- `DemoChatClient` и `DemoChatClientFactory` — детерминированный клиент для сквозного
  демо-сценария: понимает команды `write: <текст>` и `read: <текст>` и превращает их в вызовы
  `echo_write` / `echo_read` (используется Controller);
- `LlmGatewayOptions` — заготовка настроек платформенной модели (endpoint, ссылка на секрет).

**Связи** — зависит от `Core`; используется Runtime и теми сервисами, которые его
собирают (Gateway, Controller, Scheduler).

## AgentPlatform.Gateway

**Назначение** — точка входа для сообщений из канала (виджет). Принимает сообщение
визитера, находит или создаёт сессию, запускает ход агента и отдаёт ответ по SSE.

**Что внутри:**

- `POST /api/sessions/{tenantKey}/messages` — приём сообщения. Проверяется JWT виджета
  (HS256, секрет тенанта, обязательный срок действия), тенант берётся из токена;
- `GET /api/sessions/{sessionId}/stream` — SSE-поток ответа с событиями `status`,
  `delta`, `gate`, `done`; токен передаётся в query, потому что EventSource не умеет
  заголовки;
- конвейер обработки сообщения: идентификация визитера (cookie / `user_ref`), rate-limit на
  тенанта, привязка к сессии, запись сообщения в журнал, вызов Runtime, публикация ответа;
- `SessionBinder` — находит открытую сессию визитера или создаёт новую, фиксирует агента и
  его версию, берёт активный виджет-канал (или указанный), выбирает агента из конфигурации
  канала;
- `ReplyStreamHub` — журнал событий по сессии в памяти процесса (подписчик может
  подключиться до или после хода);
- rate-limit: token bucket на тенанта, счётчики в Redis (по умолчанию) или в памяти процесса
  (`Gateway:RateLimit:Storage=memory`);
- `RetryingChatClient` — повторы вызова модели перед тем, как Runtime зафиксирует
  неудачный ход; при итоге `degraded` Gateway отвечает fallback-сообщением и помечает сессию
  `degraded`;
- `UnavailableConnectorToolInvoker` — заглушка вызова тулов: из Gateway тулы недоступны.

**Связи** — использует `Runtime` (`IOrchestrationRuntime`), `Infrastructure` (сессии,
сообщения, чекпоинты, заявки), `LlmGateway` (заглушка модели) и Redis. С внешними системами
не работает — только через Connector Host, который к Gateway не подключён.

## AgentPlatform.Controller

**Назначение** — внутренний API платформы и «бэкенд» кабинета тенанта: конфигурация
агентов и коннекторов, диалоги с гейтами, расписания, служебные проверки. Именно сюда
ходит Tenant App.

**Что внутри:**

- CRUD агентов тенанта (`/api/v1/internal/tenants/{tenantId}/agents`): изменение
  публикует новую неизменяемую версию; повышение политики тула отклоняется на сервере;
- каталог коннекторов, установки и настройки тулов
  (`/connector-registry`, `/connector-installations`, `.../tool-settings`): при установке
  credentials шифруются Secret Service, создаются настройки тулов по умолчанию
  (read → гейт не требуется, остальные → гейт требуется);
- синхронизация реестра из Connector Host: при старте (фоновый сервис с повторами) и
  вручную через `POST /api/v1/internal/connector-registry/sync`;
- валидация настроек тулов `POST /api/v1/internal/tool-settings/validate` — единая проверка
  политики и режима гейта до сохранения;
- диалоги кабинета: список сессий, запуск диалога, сообщения, карточка ожидающего гейта и
  решение по нему (`approvals/{approvalId}/decision`), которое вызывает `ResumeAsync`.
  Решение разрешено только ролям admin/operator и проверяется по таблице пользователей;
- CRUD расписаний `scheduled_runs` для Scheduler (UI нет);
- служебные эндпоинты платформы: список тенантов и пользователей тенанта (для проверки seed);
- вызов тулов по MCP (`McpToolInvoker`): ищет установку, берёт endpoint (внутренний
  Connector Host для `echo` или `external_url` установки) и вызывает тул с таймаутом;
- сборка сервисов: Secret Service, порты Runtime, Runtime с демонстрационным клиентом
  модели, поддержка `--migrate` / `--seed`.

**Связи** — использует `Infrastructure`, `Runtime`, `LlmGateway` и Connector Host (по HTTP/MCP).
Используется Tenant App и внешними вызовами администратора платформы.

## AgentPlatform.TenantApp

**Назначение** — кабинет тенанта: пользовательский интерфейс для настройки агентов и
коннекторов и для работы с диалогами, включая решения по HITL-гейтам.

**Что внутри:**

- Blazor Web App с интерактивным серверным режимом; страницы: главная, «Агенты»,
  «Коннекторы», «Диалоги», карточка диалога, вход, отказ в доступе;
- аутентификация на ASP.NET Identity Core поверх существующей таблицы `users`
  (PBKDF2-хеш, роли `admin` / `operator` / `viewer`, cookie на 8 часов, блокировка после
  5 неудачных попыток). Вход и выход — обычные POST-формы с antiforgery-токеном;
- разграничение в UI и на сервере: конфигурацию меняет admin, решения по гейтам принимает
  admin и operator, viewer только смотрит;
- `ControllerApiClient` — типизированный клиент Controller API; прямых обращений к данным
  кабинета нет. Сам кабинет БД читает только для входа и служебных проверок;
- `TenantHeaderMiddleware` — определяет тенант из claim пользователя; заголовок
  `X-Tenant-Id` принимается только для анонимных dev/smoke-запросов;
- совместимые служебные эндпоинты v1 (`/api/v1/agents`, `/api/v1/approvals/pending`,
  `/api/v1/session-context`) для smoke-проверок;
- поддержка команд `--migrate` / `--seed` (используется в docker-compose для накатывания
  схемы и создания демо-тенанта).

**Связи** — зависит от `Core` и `Infrastructure` (Identity, пользователи, тенант), все
операции кабинета выполняет через Controller.

## AgentPlatform.ConnectorHost

**Назначение** — MCP-сервер платформы, за которым стоят коннекторы. Слои платформы не
ходят во внешние API напрямую — только сюда.

**Что внутри:**

- MCP-сервер на streamable HTTP с endpoint `/mcp`;
- внутренний тестовый коннектор `EchoTools`: `echo_read` (read) и `echo_write` (write, всегда
  через гейт);
- манифест коннектора (`EchoToolsManifest`), который отдаётся по
  `GET /api/v1/connectors/echo/manifest` и валидируется при старте сервиса;
- публикация JSON Schema манифеста `GET /api/v1/connectors/manifest-schema` — схема является
  артефактом платформы и используется при установке коннекторов;
- `GET /health`.

**Связи** — зависит только от `Core`. Вызывается Controller по MCP и по HTTP (получение
манифеста при синхронизации реестра). Подключение внешних MCP-серверов, health-check
установок и соблюдение лимитов — TODO следующих задач.

## AgentPlatform.Knowledge

**Назначение** — сервис знаний (RAG) для поиска по документам тенанта. Сейчас это каркас,
который фиксирует контракт и место в архитектуре.

**Что внутри:** `GET /health`; `POST /api/v1/knowledge/search` (возвращает пустой список);
`POST /api/v1/knowledge/sources/{sourceId}/reindex` (отвечает `501`). Заготовка под
pgvector-поиск и инжест.

**Связи** — зависит от `Core` и `Infrastructure`; в текущей версии никем не вызывается.

## AgentPlatform.Scheduler

**Назначение** — запуск агентов по расписанию, без входящего сообщения (например, агент
качества, который регулярно просматривает диалоги).

**Что внутри:**

- фоновый worker: раз в `Scheduler:PollIntervalSeconds` секунд (по умолчанию 30) выполняет
  один тик;
- на тике перебирает активных тенантов, читает их расписания и запускает те, чей cron уже
  наступил (точка отсчёта — последний запуск или изменение расписания). Cron — пять полей,
  время UTC;
- для запуска создаёт сессию в служебном канале `system` (создаётся один раз на тенант),
  пишет системное сообщение-триггер, выполняет ход через `IOrchestrationRuntime` и
  сохраняет ответ; итог пишется в `last_run_status` (`ok` / `error`);
- ошибка одного расписания не останавливает тик; ошибка запуска помечается в БД.

**Связи** — использует `Infrastructure` (расписания, сессии, сообщения) и `Runtime`;
модель — заглушка, тулы недоступны (`UnavailableConnectorToolInvoker`). Расписания
создаются через Controller API. Один экземпляр на установку.

## AgentPlatform.Tests

**Назначение** — автоматическая проверка правил платформы. Проект xUnit, тесты
сгруппированы по областям: политики и гейты, граф и возобновление сессий, чекпоинты и
нейтральное состояние, лимиты и деградация, манифест коннектора и его схема, маскирование
ПДн, секреты, репозитории и инварианты БД, seed, Gateway (JWT виджета, rate-limit, поток
ответов, приём сообщений), кабинет (диалоги), планировщик (cron, запуск, хранилище),
пользователи кабинета.

Тесты используют EF InMemory-провайдер и поддельные адаптеры — внешние PostgreSQL, Redis и
модель для запуска не нужны. Всего 243 теста, все проходят.

**Связи** — ссылается на все проекты решения.
