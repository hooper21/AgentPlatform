# Agent Platform — общее описание решения

Документ описывает то, что реально реализовано в репозитории на текущий момент (фаза 1 —
MVP). Это обзор для общего понимания: назначение, архитектура, функционал и границы
готовности. Детальные спецификации сюда не входят.

## 1. Назначение

Agent Platform — мультиарендная (multi-tenant) платформа для создания, хостинга и
эксплуатации AI-агентов. Платформа не содержит бизнес-логики конкретных решений:
бизнес-сценарии (например, «агент продаж») собираются из её примитивов и описываются
как шаблоны конфигураций — Solution Profiles.

Платформа даёт пять механизмов:

1. **Runtime агентов** — диалоги, вызовы инструментов (тулов), HITL-гейты (подтверждение
   человеком), чекпоинты, эскалация, передача оператору.
2. **Коннекторы** — внешние системы подключаются как MCP-серверы и описываются
   манифестом (JSON Schema манифеста, валидация при установке).
3. **Каналы** — плагины по контракту `IChannelAdapter` (виджет, Telegram, далее — другие).
4. **Знания** — RAG-инфраструктура (инжест документов, векторный поиск на pgvector).
5. **Управление** — кабинет тенанта и панель оператора платформы.

Что из этого работает в текущей версии, описано в разделе 4.

## 2. Технологический стек

- .NET 10, C#, ASP.NET Core (minimal APIs), Blazor Web App (Interactive Server) для кабинета.
- Оркестрация: `Microsoft.Agents.AI.Workflows` (Agent Framework 1.x).
- Абстракция модели: `Microsoft.Extensions.AI` (`IChatClient`).
- MCP: официальный SDK `ModelContextProtocol` 2.x, транспорт — streamable HTTP.
- Данные: PostgreSQL (в docker-образе с pgvector) + Entity Framework Core 10 / Npgsql;
  Redis (rate-limit, кеш конфигурации агента).
- Тесты: xUnit.
- Развёртывание: Docker Compose, один VPS.

Секреты и строки подключения в файлах конфигурации не хранятся — только в переменных
окружения.

## 3. Архитектура

Решение разделено на слои, каждый слой — отдельный проект solution.

```
Клиент канала (виджет)        Пользователь кабинета
        |                             |
   AgentPlatform.Gateway      AgentPlatform.TenantApp (Blazor, BFF)
        |                             |
        |                       AgentPlatform.Controller (внутренний API)
        |                             |
        +-------- AgentPlatform.Runtime (IOrchestrationRuntime, Policy Engine) ---+
                                      |
        AgentPlatform.LlmGateway (IChatClient)   AgentPlatform.Infrastructure (EF/PostgreSQL/Redis/секреты)
                                      |
                            AgentPlatform.ConnectorHost (MCP-сервер, коннекторы)
                                      |
        AgentPlatform.Scheduler (cron-запуски)   AgentPlatform.Knowledge (RAG, каркас)

                    AgentPlatform.Core — общие контракты и типы для всех слоёв
```

Ключевые архитектурные решения, которые видны в коде:

- **Слои не вызывают внешние API напрямую.** Любой внешний вызов идёт через Connector Host
  по MCP; Runtime формирует запрос на вызов тула, транспорт и секреты — на стороне коннекторов.
- **Оркестрация заменяема.** Все потребители работают через интерфейс
  `IOrchestrationRuntime` (`RunAsync`, `PauseAsync`, `ResumeAsync`). Текущая реализация —
  `MafOrchestrationRuntime` на графе Microsoft Agent Framework.
- **Состояние сессии хранится в нейтральном JSON-контракте платформы** (`messages`,
  `pending_gate`, `counters`, `version`), а не в нативных структурах рантайма. Поэтому смена
  оркестратора не требует миграции истории сессий. Сериализация идёт только через
  `StateContract`, неизвестные поля отвергаются.
- **Версия агента фиксируется на старте сессии** (version pinning). Публикация новой версии
  не меняет поведение идущего диалога и не ломает возобновление после гейта.
- **Мультиарендность.** `tenant_id` есть во всех арендных сущностях; изоляция выполняется
  tenant-фильтрованными репозиториями `ITenantScopedRepository<T>` поверх `ITenantContext`.
  Глобальные таблицы (тенанты, реестр коннекторов, шаблоны решений) обслуживает
  `IGlobalRepository<T>`.
- **Политики тулов проверяются на сервере**, а не промптом. Тулы классифицируются как
  `read` / `write` / `destructive`. Политика берётся из манифеста коннектора и может быть
  понижена настройками тенанта, но не повышена — это проверяется и при сохранении
  конфигурации, и повторно при каждом вызове тула.
- **Действия write/destructive проходят через HITL-гейт**: создаётся заявка в `approvals`
  со статусом `pending`, сессия ставится на паузу с чекпоинтом, решение (подтвердить /
  отклонить) возвращается в Runtime через `ResumeAsync`.
- **Секреты тенантов шифруются** (AES-256-GCM) и хранятся в БД только в зашифрованном виде;
  в логи, API и конфигурацию попадает лишь ссылка на секрет. Аргументы тулов маскируются от
  персональных данных перед записью в заявку и карточку подтверждения.
- **Наблюдаемость подготовлена, но не включена**: в схеме БД есть поля для корреляции
  трассировок (`tool_audit.trace_id`), при этом OpenTelemetry/Jaeger в коде не подключены.

## 4. Функционал по механизмам

### 4.1. Runtime агентов — реализован

Ход диалога исполняется графом: старт хода → диалог (LLM) → условный переход на вызов
тула (read), на гейт (write/destructive) или на эскалацию → завершение.

Поддерживается:

- обработка сообщения с историей диалога и активными тулами версии агента;
- серверное определение необходимости подтверждения (в том числе по условию на аргументы
  вызова для режима `conditional`; ошибка условия трактуется как «подтверждение нужно»);
- пауза с сохранением чекпоинта, заявкой `approvals` и карточкой подтверждения;
  ожидающая сессия не держит поток;
- возобновление после решения (подтверждено / отклонено / истекло / заменено), в том числе
  после рестарта сервиса — состояние лежит в PostgreSQL;
- лимиты версии агента (`max_turns`, `max_tool_calls`, `max_tokens`) и эскалация при
  деградации (порог неудачных ходов);
- срок жизни гейта по умолчанию 24 часа с возможностью переопределения для тенанта;
- итог хода: `completed`, `paused_for_gate`, `escalated`, `degraded`.

### 4.2. Коннекторы — реализованы на примере внутреннего тестового коннектора

Реализовано: манифест коннектора с JSON Schema и валидацией, каталог коннекторов,
установка коннектора в тенанте с шифрованием credentials, настройки тулов (политика и
режим гейта), вызов тулов по MCP (streamable HTTP) из Controller, публикация тулов в
модель по манифесту.

В поставке один коннектор — `echo` (EchoTools): read-тул `echo_read` и write-тул
`echo_write`, который всегда проходит через гейт. Он используется для проверки графа,
политик и HITL-сценария.

Ещё не реализовано: подключение внешних MCP-серверов с их health-check, соблюдение
декларированных лимитов (очередь на пару tenant × connector, ретраи, кеш read-тулов),
внутренний коннектор `platform-ops`.

### 4.3. Каналы

Контракт канала (`IChannelAdapter`) зафиксирован: приём сообщения, стриминг ответа,
карточка подтверждения, уведомление об эскалации. Канал не знает о сессиях и не содержит
бизнес-логики.

Фактически работает транспорт виджета на стороне Gateway: приём сообщения с JWT виджета,
rate-limit на тенанта, привязка визитера к сессии, отдача ответа по SSE. Дополнительно
есть служебные типы каналов: `cabinet` (диалоги из кабинета тенанта, создаётся
автоматически) и `system` (плановые запуски Scheduler). Канал Telegram не реализован.

Отдельной реализации `IChannelAdapter` для виджета или Telegram в коде пока нет: логика
виджета сосредоточена в Gateway.

### 4.4. Знания — каркас

Сервис Knowledge Service поднимается и отвечает на `GET /health`. Метод поиска
`POST /api/v1/knowledge/search` возвращает пустой результат, переиндексация источника
отвечает `501 Not Implemented`. Таблицы `knowledge_sources` и `knowledge_chunks` в схеме
БД есть, инжест и векторный поиск на pgvector — задача следующей фазы.

### 4.5. Управление

Кабинет тенанта (Blazor) — реализован: вход по логину и паролю, роли `admin` / `operator` /
`viewer`, страницы «Агенты», «Коннекторы», «Диалоги» и карточка диалога с гейтом.
Все операции кабинет выполняет через внутренний API Controller.

Панель оператора платформы — не реализована (есть только внутренние API-эндпоинты
платформы: список тенантов, пользователей, реестр коннекторов, расписания).

### 4.6. Планировщик

Реализован сервис Scheduler: раз в N секунд перебирает активных тенантов, читает
расписания `scheduled_runs` (cron из пяти полей, время UTC), запускает сессию агента без
входящего сообщения, пишет системный триггер в историю и сохраняет итог запуска.
Управление расписаниями — через Controller API; отдельного UI нет.

## 5. Сквозной сценарий, который работает сейчас

1. В кабинете тенанта создаётся агент: имя, системный промпт, модель, лимиты, включённые
   тулы с политиками и режимом гейта. Сохранение публикует версию.
2. В разделе «Коннекторы» устанавливается коннектор `echo`; credentials (если заданы)
   шифруются и в API больше не возвращаются.
3. В разделе «Диалоги» создаётся диалог и отправляется сообщение (для демонстрационного
   клиента модели команда вида `write: <текст>` или `read: <текст>`).
4. Read-тул исполняется сразу. Write-тул создаёт заявку, и сессия переходит в
   `awaiting_gate`; в карточке видны маскированные аргументы и срок истечения.
5. Пользователь с ролью admin или operator подтверждает или отклоняет действие. Runtime
   возобновляет сессию с чекпоинта: при подтверждении тул исполняется, при отказе диалог
   продолжается без действия.
6. История диалога, чекпоинты и заявки остаются в PostgreSQL — пауза и подтверждение
   переживают рестарт сервиса.

Тот же ход можно провести через Gateway по каналу виджета (`POST` сообщения → `GET`
SSE-поток), если у тенанта есть активный виджет-канал.

## 6. Границы текущей версии (что пока заглушка)

- **Модель.** Реальный провайдер LLM не подключён. Controller использует
  детерминированный `DemoChatClient` (команды `write:` / `read:`), Gateway и Scheduler —
  `StubChatClient`. Абстракция `IChatClientFactory` и обёртка `PlatformChatClient` для
  выбора модели, учёта токенов и трейсинга готовы, но наполнение — следующая фаза.
- **KMS.** Мастер-ключ AES-256 читается из переменной окружения; при её отсутствии
  используется dev-ключ с предупреждением в лог. Реальный KMS и версионирование ключей — TODO.
- **Секреты виджета.** Gateway берёт секрет подписи JWT тенанта из конфигурации
  (переменные окружения), а не из Secret Service.
- **Поиск знаний, инжест, панель оператора платформы, тарифы и учёт usage** — не реализованы;
  соответствующие таблицы (`usage`, `knowledge_*`, `solution_profiles`, `tool_audit`)
  созданы миграциями, но код в них пока не пишет.
- **Аудит и метрики.** Append-only аудит вызовов тулов и поля трассировок заведены в схеме,
  но запись аудита и OpenTelemetry в коде отсутствуют.
- **SSE-поток** отдаёт готовый ответ событиями (`status`, `delta`, `gate`, `done`);
  потоковая генерация от модели не подключена. Журнал потока хранится в памяти процесса
  Gateway, то есть корректно работает при одной реплике.
- **Scheduler** не координирует несколько экземпляров: в v1 запускается один.
- **Тулы из Gateway и Scheduler недоступны**: там зарегистрирован
  `UnavailableConnectorToolInvoker`. Тулы работают в цепочке кабинет → Controller →
  Connector Host.
- **Кеш конфигурации агента** живёт 60 секунд; метод явной инвалидации есть, но пока не
  вызывается при сохранении конфигурации.
- Внешние MCP-коннекторы, лимиты и кеш тулов, Telegram, heartbeat для SSE — задачи фазы 2
  и далее, в коде отмечены как `TODO`.
