Разберу работу решения «агент продаж» поверх платформы — не как список требований, а как живую систему: кто что делает, в каком порядке, что происходит на каждом шаге и как система ведёт себя, когда что-то ломается. Это взгляд архитектора на рантайм: сценарии, последовательности, потоки данных и режимы деградации.

## Общая картина

Три контура работы:

1. **Диалоговый контур** (событийный): клиент пишет → агент отвечает. Горячий путь, меряется секундами.
2. **Контур подтверждений** (асинхронный): агент хочет изменить данные → ждёт человека → продолжается. Холодный путь, меряется часами.
3. **Контур качества** (плановый): Scheduler запускает агента-аудитора раз в неделю → тот анализирует диалоги и предлагает улучшения конфигурации через гейт.

Все три контура работают на одном runtime и различаются только тем, что запускает сессию: входящее сообщение (1, 2) или cron (3).

## Сценарий 1. Простой диалог (горячий путь)

Клиент на сайте спрашивает: «Есть ли фильтр АР-200 в наличии?»

```
Виджет ──► Gateway ──► Runtime ──► LLM Gateway ──► Connector Host ──► МойСклад
   ▲          │            │
   └──────────┴────────────┘  (SSE-стриминг ответа)
```

Пошагово:

1. **Виджет** отправляет сообщение c JWT (HS256, секрет виджета тенанта). Gateway проверяет подпись, определяет тенанта, rate-limit по токен-бакету в Redis.
2. **Gateway** находит или создаёт сессию (`sessions`, привязка по `user_ref` из cookie). Сессия несёт `agent_version` — версию конфигурации, на которой диалог начался.
3. **Runtime** подтягивает конфигурацию агента из кеша Redis (TTL 60 с; промпт, активные тулы, правила). Собирает агента: `IChatClient` из `llm_config` тенанта + тулы подключённых коннекторов.
4. **Роутер моделей**: ход классифицируется как SIMPLE/COMPLEX (промпт Р5). Вопрос о наличии — COMPLEX, идёт на сильную модель.
5. **DialogExecutor**: модель решает вызвать тул `ms_get_stock(productQuery: "АР-200")`. Политика `read` — исполнение без гейта.
6. **Connector Host**: тул идёт в очередь пары «тенант × МойСклад» → кеш Redis (TTL 15 мин, класс `stock`) → при промахе запрос в API МойСклад с учётом веса (отчёт остатков = 5 единиц квоты). 429/5xx → ретраи с backoff → при исчерпании ответ из кеша с пометкой `cached=true, asOf`.
7. **DialogExecutor** формирует ответ строго из результата тула, стримит в канал. Пишутся: `messages`, `tool_audit` (с маскированием аргументов и `trace_id`), инкремент `usage`.
8. Проверяются **триггеры эскалации** — здесь не сработали, сессия остаётся `active`.

Ключевое архитектурное свойство: узлы stateless, всё состояние сессии после каждого суперстепа уходит в `checkpoints` (нейтральный JSON). Падение любого узла в середине — не потеря диалога, а resume.

## Сценарий 2. Write-операция: гейт подтверждения (холодный путь)

Клиент просит оформить заказ. Это `write`-тул — путь длиннее и асинхронный.

1. Модель формирует вызов `ms_create_order_draft(...)` с аргументами.
2. **Policy Engine** (серверно, не промптом) видит политику `write` и `gate_settings` тула: `conditional` — спрашивать при сумме > 10 000 ₽. Предикат применяется к аргументам: сумма проходит → требуется подтверждение.
3. **GateExecutor**: собирает `GatePayload` (тул, маскированные аргументы, человекочитаемое описание — генерируется промптом Р2), пишет `approvals` со статусом `pending` и ссылкой на текущий чекпоинт, **приостанавливает workflow**. Сессия переходит в статус `awaiting_gate`.
4. Карточка подтверждения уходит в канал — в виджет клиенту и/или в Telegram оператору (настройка тенанта).
5. **Сессия «замораживается»**: строка в БД, ноль вычислительных ресурсов. Может стоять секунды или сутки — это не таймаут воркера, а запись в таблице.
6. Клиент подтверждает → Gateway вызывает `ResumeAsync(session, Approved)` → Runtime загружает чекпоинт, валидирует `graph_signature_hash`, исполняет тул, результат возвращается агенту, диалог продолжается.
7. `approvals` закрывается (`approved`, кем, когда) — это уже аудиторский след, не только операционный.

Edge-cases, которые архитектура покрывает явно:

| Ситуация | Поведение |
|---|---|
| Подтверждение пришло после рестарта сервиса | Resume из чекпоинта — рестарт не влияет |
| Клиент подтвердил через 3 дня | Работает: срок жизни гейта — настройка (дефолт 24 ч, потом `expired`) |
| Конфигурация агента изменилась за время ожидания | Version pinning: сессия продолжает на исходной версии |
| Сумма ниже порога условного гейта | Исполняется без паузы — гейты не душат конверсию |
| Тул отклонён | Агенту передаётся «действие отклонено», он предлагает альтернативу в диалоге |

## Сценарий 3. Эскалация и takeover

Триггеры (тональность, 3 неуспешных хода, запрос человека) срабатывают после каждого хода:

1. **EscalateExecutor** собирает контекст: история, карточка лида из правил, вызванные тулы, показанные данные.
2. Промпт Р3 генерирует резюме для менеджера (суть / сделано / не сделано / следующий шаг / тональность).
3. Доставка: Telegram-чат оператора + карточка в кабинете. Debounce 60 с — не дублируем на каждую реплику.
4. Сессия → `escalated`, агент замолкает до решения.
5. **Takeover**: оператор подключается, пишет от себя; после закрытия агент получает резюме (Р4) и продолжает — обязательства менеджера не пересматриваются.

Важная деталь: эскалация не «закрывает» диалог, а передаёт билд — контекст не теряется ни при ручном takeover, ни при возврате агенту.

## Сценарий 4. Контур качества (плановый)

Понедельник 06:00, Scheduler запускает агента `quality-auditor` без входящего сообщения:

1. Агент читает данные через внутренний коннектор `platform-ops`: статистику тулов, эскалации, «вопросы без ответа» за неделю.
2. Находит закономерности (минимум 3 наблюдения на вывод — правило промпта Р6): например, «14 отказов назвать цену — тул цен стабильно возвращал 429» или «вопросы про доставку СДЭК без ответа — база знаний пуста».
3. Формирует предложение через `ops_propose_agent_update` → это `write`-тул → **тот же гейт**: карточка «применить изменение промпта?» уходит админу тенанта.
4. После подтверждения создаётся новая версия агента (`agent_versions`, статус `proposed` → `published`). Откат — переключение указателя, без миграций.

Архитектурная красота здесь в том, что агент качества использует те же примитивы, что и агент продаж: тот же runtime, те же гейты, тот же аудит. И корректирующая петля замкнута: диалоги → анализ → предложение → подтверждение человека → новая версия → влияние виден на следующем прогоне.

## Режимы деградации

Система спроектирована так, что каждая внешняя зависимость имеет отказ-safe поведение:

| Отказ | Поведение |
|---|---|
| LLM недоступна | Ретраи → fallback «менеджер ответит лично» + сбор контакта, сессия `degraded` |
| API МойСклад/amoCRM (429, 5xx) | Ретраи в коннекторе → ответ из кеша с пометкой возраста → при пустом кеше честное «уточню и вернусь» |
| Gateway упал | Сессии в чекпоинтах, рестарт — resume, клиенту просто «медленнее отвечает» |
| Коннектор недоступен длительно | PF15: статус на дашбордах, тул исключается из активных, агент отвечает без него по базе знаний |
| Кеш конфигурации устарел | TTL 60 с + инвалидация при изменении конфига — расхождение максимум 60 с |

Принцип: **нет сценария «агент молчит»**. Любой отказ конвертируется либо в деградированный, но честный ответ, либо в передачу человеку.

## Развёртывание и производительность (операционный взгляд)

- **Топология MVP:** один VPS, Compose: gateway + runtime + connector host + knowledge + tenant app + PostgreSQL + Redis + LLM-нода. Планка — 5–10 активных тенантов.
- **Бюджет латентности горячего пути (p95):** простой вопрос ≤ 3 с, вопрос с тул-вызовом ≤ 8 с. Основные слагаемые: роутинг модели (дешёвая/сильная), кеш конфига (нет похода в БД на каждый ход), кеш read-данных (нет похода во внешний API на повторный вопрос).
- **Масштабирование:** runtime и connector host stateless — растут горизонтально; состояние целиком в PostgreSQL/Redis. Первое узкое место обычно не агенты, а GPU-нода LLM — поэтому SIMPLE/COMPLEX-роутинг даёт двойной выигрыш: экономит GPU и снимает нагрузку.
- **Наблюдаемость:** каждый ход — OTel-трейс «сообщение → узлы графа → тул → ответ», связанный с `tool_audit` через `trace_id`. По трейсу + чекпоинтам любая сессия воспроизводится (replay) — это главный инструмент разбора инцидентов «почему агент сказал клиенту X».

## Связность всего решения в одном абзаце

Клиент общается с агентом в виджете; агент отвечает только по данным из коннекторов; любые изменения данных проходят через серверный гейт с подтверждением человека; всё, что агент сделал, зафиксировано в аудите и воспроизводимо по трейсам; раз в неделю внутренний агент анализирует работу первого и предлагает улучшения через тот же гейт; человек подтверждает — создаётся новая версия агента с возможностью отката. Каждый элемент этой петли опирается на примитив платформы, а не на код конкретного решения — поэтому вторая ниша собирается конфигурацией, а не разработкой.
