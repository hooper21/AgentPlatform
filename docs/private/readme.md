# Agent Platform — техническое описание платформы AI-агентов

**Версия документа:** 2.0 · **Дата:** ноябрь 2026 · **Статус:** на согласование

## 1. Определение и назначение

**Agent Platform** — мультиарендная платформа для создания, настройки, хостинга и эксплуатации AI-агентов, которые работают с внешними системами через MCP-серверы и общаются с пользователями через встраиваемые каналы (чат-виджет, мессенджеры).

Платформа **не содержит бизнес-логики конкретного решения**. Она предоставляет пять механизмов:

1. **Runtime агентов** — исполнение диалогов с вызовом тулов, гейтами подтверждения, памятью сессий.
2. **Механизм коннекторов** — подключение любой внешней системы как набора MCP-тулов без изменения кода платформы.
3. **Каналы** — подключение агента к точкам контакта с пользователями.
4. **Знания** — придание агенту знаний тенанта (документы, сайты, FAQ).
5. **Управление** — кабинет для сборки, настройки, наблюдения и контроля расходов.

Бизнес-решения («агент продаж», «агент клиники», «агент поддержки») собираются поверх платформы как **конфигурации и шаблоны** — см. раздел 9.

**Принципы дизайна:**

- **П1. Данные не придумываются.** Агент отвечает только по данным из тулов или базы знаний; режим валидации включается конфигурацией.
- **П2. Write-операции — через гейт.** Любое изменение данных внешних систем — только после явного подтверждения; запреты живут на сервере, а не в промпте.
- **П3. Эскалация человеку обязательна.** Агент умеет выходить из диалога, передавая человеку полный контекст.
- **П4. Мультиарендность с изоляцией.** Данные, секреты, конфигурации и лимиты тенантов не пересекаются.
- **П5. Расширяемость без правки ядра.** Новый коннектор, канал или модель — плагин или конфигурация.

## 2. Границы платформы

| Входит в платформу | Не входит в платформу |
|---|---|
| Runtime агентов, оркестрация, чекпоинты, HITL | Бизнес-сценарии (квалификация лидов, скрипты продаж) |
| Реестр, хостинг и жизненный цикл MCP-коннекторов | Бизнес-коннекторы как таковые (поставляемые модули, раздел 9) |
| Каналы: виджет сайта, Telegram | Контент баз знаний тенантов |
| RAG-инфраструктура: инжест, индексация, поиск | Конкретные промпты и правила — конфигурация тенантов |
| Мультиарендность, безопасность, учёт расходов | Биллинг-движок в MVP (учёт ведётся, списание — фаза 4) |
| Кабинет тенанта, панель оператора платформы | — |

## 3. Роли

| Роль | Что делает |
|---|---|
| **Пользователь агента** | Человек на сайте или в мессенджере: ведёт диалог, подтверждает действия агента (если так настроено) |
| **Оператор-человек** | Сотрудник тенанта: подтверждает write-операции (HITL), делает takeover, забирает эскалации |
| **Администратор тенанта** | Создаёт агентов: подключает коннекторы, каналы, модели; редактирует промпты, знания, правила гейтов и эскалации; смотрит аналитику |
| **Разработчик коннектора** | Реализует MCP-сервер по манифесту платформы, публикует в реестр (внутренний или сторонний) |
| **Оператор платформы** | Ваша команда: управление тенантами, тарифами, релизами коннекторов, мониторинг |

## 4. Функциональные требования

### 4.1. Runtime агентов

- **PF1. Конфигурируемый агент.** Агент = объект конфигурации: системный промпт, модель, набор тулов подключённых коннекторов, база знаний, правила эскалации, лимиты. Изменение — через кабинет, без деплоя.
- **PF2. Версии конфигурации.** Каждое изменение создаёт версию; к сессии привязана начальная версия агента. Откат — кнопкой.
- **PF3. Диалоговые сессии.** Сессия переживает рестарт узла, паузы любой длительности, возвращение пользователя через дни (чекпоинт-модель).
- **PF4. Вызов тулов.** Агент вызывает тулы подключённых MCP-серверов; платформа классифицирует тулы по политике: `read` / `write` / `destructive`.
- **PF5. Гейты подтверждения (HITL).** Для `write`/`destructive`-тулов платформа приостанавливает сессию, показывает карточку действия оператору и/или пользователю (настройка), ждёт решения неограниченно долго, возобновляет исполнение по ответу. Настройки на уровне тул-политики: «всегда спрашивать», «спрашивать при условии (сумма > N, тип операции)», «не спрашивать».
- **PF6. Эскалация.** Настраиваемые триггеры: тональность, N неудачных ходов, явный запрос человека, выход за рамки тем. Оператор получает историю, вызовы тулов и показанные данные.
- **PF7. Takeover.** Оператор подключается к живому диалогу в любой момент; агент замолкает до явного возврата; после закрытия агент продолжает с учётом истории.
- **PF8. Лимиты.** Лимит ходов на сообщение, тул-вызовов на сессию, токенов — настраиваемые; превышение → вежливое завершение + эскалация.
- **PF9. Валидация данных.** Режим «данные только из тулов»: числа/цены в ответе сверяются с результатами тул-вызовов; расхождение → перегенерация или пометка.

### 4.2. Коннекторы (MCP)

- **PF10. Реестр коннекторов.** Каталог: описание, список тулов, схема подключения (OAuth / API-ключ / свой эндпоинт). Установка — мастер в кабинете за несколько шагов.
- **PF11. Жизненный цикл.** Версионирование коннекторов; поддержка N версий одновременно (миграция без простоя); окончание поддержки — видимое в кабинете.
- **PF12. Изоляция секретов.** Токены тенантов шифруются (AES-256, KMS); коннектор получает их через контролируемый доступ; в логах и трейсах секретов нет.
- **PF13. Тул-политика.** Для каждого тула: включён/выключен, политика (понижаемая, не повышаемая), переопределение описаний под специфику бизнеса тенанта.
- **PF14. Лимиты и устойчивость.** Очередь запросов на пару «тенант × коннектор», ретраи с backoff, кеш read-результатов с TTL по классу данных; лимиты внешнего API коннектор декларирует в манифесте, платформа их уважает.
- **PF15. Health-мониторинг.** Статус (ок / деградация / недоступен), счётчики ошибок и 429, время последнего успешного вызова — на дашбордах тенанта и оператора.
- **PF16. Сторонний MCP-сервер.** Тенант может подключить внешний MCP-сервер по URL; платформа проверяет манифест и включает тулы в агента.

### 4.3. Каналы

- **PF17. Чат-виджет.** JS-сниппет: брендирование, мобильная адаптация, идентификация визитера (cookie/localStorage; связывание с внешним контактом после передачи телефона).
- **PF18. Telegram-бот.** Подключение бота тенанта; тот же диалог и контекст, что в виджете.
- **PF19. Абстракция канала.** Каналы — плагины с единым контрактом: входящее сообщение → привязка к сессии → стриминг ответа → отображение карточек подтверждения/эскалации. Новый канал — без правки ядра.
- **PF20. Сквозной контекст.** Один пользователь на сайте и в Telegram — одна сессия при совпадении идентификатора.

### 4.4. Знания

- **PF21. Источники.** Документы (PDF, DOCX, MD, TXT), страницы сайта по URL, ручные FAQ.
- **PF22. Инжест-пайплайн.** Чанкинг → эмбеддинги → индекс (pgvector); переиндексация по расписанию или вручную; статус виден в кабинете.
- **PF23. RAG-конфигурация.** Глубина поиска, порог релевантности, приоритет живых данных из тулов над статичными знаниями.
- **PF24. Цитируемость.** Ответ может ссылаться на источник знаний; настраивается на агента.

### 4.5. Наблюдаемость и контроль

- **PF25. Аналитика.** Диалоги, длительность, доля завершённых/эскалированных, топ-вопросы, вопросы без ответа (кандидаты в базу знаний).
- **PF26. Аудит.** Append-only журнал: тул-вызовы (с маскированием ПДн), решения гейтов (кто, когда, что подтвердил), эскалации.
- **PF27. Трейсинг.** OpenTelemetry: сквозной трейс «сообщение → узлы графа → тул → ответ»; упрощённый viewer в кабинете + экспорт в Jaeger/Grafana.
- **PF28. Расходы.** Учёт токенов, тул-вызовов и диалогов в разрезе агентов и периодов; лимиты и алерты по квоте тарифа.

### 4.6. Мультиарендность и администрирование

- **PF29. Управление тенантами** в панели оператора: создание, тариф, квоты, блокировка.
- **PF30. Роли внутри тенанта:** admin (всё), operator (диалоги, гейты, эскалации), viewer (аналитика). Приглашения по email.
- **PF31. Экспорт данных** (диалоги, аудит, конфигурации) в JSON/CSV.
- **PF32. Режим «свой LLM».** Тенант подключает OpenAI-совместимый эндпоинт (Ollama/vLLM/облако) или API-ключ; данные не идут на сторонние API без его ведома.

## 5. Нефункциональные требования

| Категория | Требование |
|---|---|
| Производительность | Time-to-first-token ≤ 3 с (без тулов), ≤ 8 с (с тул-вызовом), p95 |
| Пропускная способность | ≥ 50 одновременных активных сессий на узел оркестратора; масштабирование горизонтальное |
| Доступность | 99% (стадия MVP); падение внешнего API → fallback («ответит оператор»), не отключение |
| Отказоустойчивость | Чекпоинт после каждого суперстепа; сессия восстанавливается после рестарта любого узла; ожидающие HITL-сессии не потребляют вычислительных ресурсов |
| Безопасность | ПДн в РФ (152-ФЗ); маскирование ПДн в логах; шифрование секретов; tenant-изоляция на всех слоях (БД, кеши, очереди, индексы знаний) |
| Безопасность | Промпт-инъекции: контент знаний и результаты тулов подаются модели как данные; запреты дублируются серверным policy engine |
| Масштабируемость | Все сервисы stateless (состояние в PostgreSQL/Redis); коннекторы по HTTP масштабируются независимо |
| Расширяемость | Новый коннектор и канал — без изменения ядра; новый сценарий — только конфигурация |
| Обновляемость | Rolling-деплой без разрыва сессий: graceful shutdown — доработка суперстепа, сохранение возобновляемого чекпоинта |
| Портируемость оркестрации | State сессий сериализуется в нейтральный JSON-контракт платформы (не в нативный формат рантайма) — смена оркестратора не требует миграции истории сессий |
| Аудитопригодность | Replay: по trace_id + чекпоинтам сессия проигрывается шаг за шагом |
| Развёртывание | Docker Compose (MVP, VPS в РФ) → разделённые сервисы (рост) → on-prem-пакет (фаза 4) |
| Совместимость | MCP-спецификация 2026-07-28 (stateless-ядро); коннекторы тестируются независимым MCP-клиентом |

### 6.3. Оркестрационный слой (замена LangGraph/LangChain)

Оркестрация агентов — **заменяемый модуль** за внутренним интерфейсом `IOrchestrationRuntime`. Архитектура описана в терминах примитивов графовой оркестрации, реализуемых одним из рантаймов:

| Примитив платформы | .NET-реализация (основной вариант): Microsoft Agent Framework | Python-реализация (альтернатива): LangGraph / LangChain |
|---|---|---|
| Граф `dialog → tool → gate → escalate` | Workflow, исполнители, детерминированные переходы | `StateGraph`, узлы-функции, `add_conditional_edges` |
| Типизированное состояние сессии | Типизированный state-объект workflow | `TypedDict` + редьюсер `add_messages` |
| Вызов тулов | Тул-исполнители workflow, тулы MCP через `AIFunction` | `ToolNode`, `tools_condition`, `bind_tools` |
| Чекпоинты и resume | Checkpoint storage (PostgreSQL), снапшот после суперстепа, `graph_signature_hash` | `Checkpointer` (`PostgresSaver`), `thread_id` |
| Гейт подтверждения (PF5) | Встроенный human-in-the-loop на уровне workflow | `interrupt()` + `Command(resume=…)` |
| Graceful shutdown | Встроен в runtime MAF | Перехват перед следующим суперстепом |
| Подключение MCP | Официальный `ModelContextProtocol` C# SDK, тулы → агент напрямую | `langchain-mcp-adapters` (`MultiServerMCPClient`) |
| Сборка агента из конфига (PF1) | `chatClient.AsAIAgent(...)` → `ChatClientAgent` | `create_agent` (только для прототипов) |
| Трейсинг | OpenTelemetry (встроен) | LangSmith / OpenTelemetry |

**Выбор рантайма.** Основной — `Microsoft.Agents.AI.Workflows`: соответствует стеку команды (.NET), покрывает все примитивы таблицы, поддерживается Microsoft (Semantic Kernel и AutoGen переведены в maintenance-режим — новые фичи только в Agent Framework). LangGraph/LangChain — запасной вариант на случай осознанного перехода на Python-стек: меняются реализации в таблице, слои Gateway, Connector Host, Knowledge и модель данных остаются без изменений благодаря контракту `IOrchestrationRuntime` и нейтральному формату чекпоинтов (требование «портируемость оркестрации», раздел 5).

**Почему не LangChain как основа.** LangChain (`create_agent`) закрывает только стандартный цикл «LLM ↔ тулы» без явного контроля переходов. Требования PF5 (ожидание любой длительности), PF7 (takeover) и PF9 (серверная валидация) — это явные узлы и переходы, то есть территория LangGraph/Workflows.

Эквивалентность графа на двух рантаймах:

```python
# Python / LangGraph — для сравнения
builder = StateGraph(AgentState)
builder.add_node("dialog", dialog_node)
builder.add_node("tools", ToolNode(read_tools))
builder.add_node("gate", gate_node)          # interrupt()
builder.add_node("escalate", escalate_node)
builder.add_conditional_edges("dialog", route)
builder.add_edge("tools", "dialog")
app = builder.compile(checkpointer=PostgresSaver.from_conn_string(DB_URL))
```

```csharp
// C# / Microsoft Agent Framework — основной вариант
var workflow = AgentWorkflowBuilder.BuildSequential(
    dialogExecutor,      // LLM-ход
    toolExecutor,        // read-тулы из MCP
    gateExecutor,        // write-гейт: приостановка + ожидание решения
    escalateExecutor);   // передача оператору с контекстом
// Чекпоинт: снапшот после каждого суперстепа, resume по чекпоинту
```

Структура одна — меняется только API. Это позволяет пилотам на n8n проверять промпты, тулы и сценарии (переносятся между рантаймами), а не «технологию».

### 6.4. Контракты расширения

Три интерфейса, на которых держится расширяемость:

1. **Контракт коннектора** — манифест MCP-сервера: тулы с JSON-схемами и описаниями, декларация лимитов внешнего API, классификация по политикам, классы кешируемых данных с TTL. Проверяется при установке.
2. **Контракт канала** — плагин: приём сообщения с идентификацией пользователя → привязка к сессии → стриминг ответа → карточки подтверждения/эскалации.
3. **Контракт модели** — `IChatClient` (OpenAI-совместимый эндпоинт): любая локальная или облачная модель подключается конфигурацией.

Всё остальное (промпты, правила, активные тулы, знания) — данные, а не код.

### 6.5. Жизненный цикл сессии (happy path)

1. Канал доставляет сообщение → Gateway определяет тенанта → открывает/возобновляет сессию (`thread_id`).
2. Runtime загружает конфигурацию агента (кеш Redis, TTL 60 с) и собирает агента: промпт + активные тулы + правила.
3. Узел `dialog`: модель отвечает или вызывает тул; роутинг модели — простой ход на дешёвую, сложный на сильную.
4. Policy engine проверяет класс тула: `read` — исполняется; `write`/`destructive` — узел `gate` приостанавливает workflow, чекпоинт сохранён, карточка подтверждения уходит в канал.
5. Подтверждение (через секунду или сутки) → resume с точного места → тул-вызов через Connector Host → нормализованный результат или явная ошибка.
6. Ответ стримится в канал; пишутся аудит и usage.
7. Триггеры эскалации проверяются после каждого хода.

### 6.7. Развёртывание

- **Стадия 1 (MVP):** Docker Compose на одном VPS в РФ: gateway, runtime, connector host, knowledge, tenant app, PostgreSQL, Redis, LLM-нода (Ollama на CPU или vLLM на GPU-ноде). Хватает на 5–10 активных тенантов.
- **Стадия 2:** выделение сервисов, балансировка, отдельная GPU-нода, второй канал.
- **Стадия 3:** on-prem-пакет (Compose/Helm) для enterprise-тенантов.

## 7. Ключевые риски и ответы архитектуры

| Риск | Ответ |
|---|---|
| Лимиты внешних API (429, взвешенные квоты) | Очередь + кеш + приоритизация в коннекторе; деградация «ответ из кеша с пометкой» |
| Галлюцинации модели | П1, режим PF9, жёсткий промпт, аудит тул-вызовов |
| Промпт-инъекция через контент | Контент RAG как данные; запреты дублируются policy engine |
| Долгий HITL | Чекпоинт-модель: ожидающая сессия — строка в БД, не воркер |
| Смена спецификации MCP | SDK-слой изолирован в Connector Host |
| Падение внешнего API | Fallback-режим канала + статус коннекторов на дашборде |
| Привязка к рантайму оркестрации | Контракт `IOrchestrationRuntime` + нейтральный формат чекпоинтов |

## 8. Срез скоупа MVP

**Входит:** runtime агента с гейтами и чекпоинтами, виджет сайта, коннекторы МойСклад + amoCRM по манифестам, база знаний (документы + сайт), кабинет (онбординг, конфиг агента, дашборд), аудит, usage, эскалация в Telegram, тариф «пилот».

**Сознательно не входит:** drag-and-drop-редактор сценариев (только простая форма), суб-агенты, А/Б-тесты промптов, self-hosting, публичный каталог коннекторов, биллинг-движок, телефония.

## 9. Решение «агент продаж» как конфигурация платформы

| Элемент решения | Примитив платформы |
|---|---|
| Коннектор МойСклад (10 тулов: 7 read, 3 write) | MCP-коннектор в реестре, манифест с политиками |
| Коннектор amoCRM (11 тулов, долгосрочный токен, автоподгрузка кастомных полей) | MCP-коннектор в реестре |
| Агент-продавец | Агент (PF1): промпт «консультант», активные тулы, лимиты |
| База знаний тенанта | Knowledge Sources |
| Правила квалификации лида | Rules агента + структурированный вывод |
| Гейт на создание сделки/счёта | Тул-политика write → подтверждение |
| Передача тёплого лида менеджеру | Escalation rules (PF6) |
| Виджет на сайте | Канал «виджет» (PF17) |
| Шаблон «Sales Agent profile» | Сохраняемая конфигурация (агент + коннекторы + знания), разворачиваемая онбординг-мастером за один сеанс |

Шаблоны — то, что превращает платформу в тиражируемый продукт: вторая ниша (клиники, доставка) = ещё один шаблон, а не новая разработка.

## 10. Дорожная карта

1. **Фаза 1 — ядро платформы (4–6 недель):** runtime агента с одним тестовым коннектором, виджет, сессии с чекпоинтами, гейт write с подтверждением в чате, MVP кабинета (конфиг агента, подключение коннектора).
2. **Фаза 2 — коннекторы и знания (3–4 недели):** МойСклад + amoCRM по манифестам, knowledge-сервис, Telegram-канал, аудит, usage.
3. **Фаза 3 — решение «агент продаж» (2–3 недели):** шаблон Sales Agent profile, онбординг-мастер, дашборд; параллельные пилоты на n8n как эталон сценариев.
4. **Фаза 4 — платформа как продукт:** реестр коннекторов, сторонние MCP-серверы, роли, биллинг-движок, on-prem-пакет.
